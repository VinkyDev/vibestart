Delivery is how the finished application reaches its users: through Docker on a server, Void on Cloudflare, or an Electron desktop app. Each is optional; Docker and Void can also be added to compatible existing projects.

## Docker [#docker]

<Tech href="https://docs.docker.com" icon="docker" />

Selecting Docker adds a production Dockerfile, Compose configuration, and ignore file. Multi-stage builds separate dependency installation, application builds, and the runtime. The build stage installs and builds only the apps the image runs and the packages they use, so an Electron app in the same repository stays out. The final image contains the output needed to run the application.

Output follows the selected stack: static sites use a web server, SSR applications run their server build, and Hono uses the selected Node.js or Bun runtime. Database files and service data directories use persistent storage.

Configure secrets and database addresses in the deployment environment, then start services with the generated Compose configuration. Add deployment files to an existing project with [`npx vibestart-cli add docker`](/docs/cli/add).

## Void (preview) [#void]

<Tech href="https://void.cloud" icon="void" />

Void 1.3.0 builds and deploys to your own Cloudflare Workers account. Choose `--deployment void --runtime workers` for a static SPA, a SPA hosted by Hono, or TanStack Start. Next.js, a standalone Hono server, and TanStack Start paired with Hono are excluded. A static SPA deploys as assets alone. With Hono, Cloudflare serves the SPA's assets and runs the Worker only for `/api/*`, so oRPC is served at `/api/rpc`.

Database-backed server stacks use Drizzle with an external PostgreSQL or MySQL database, optionally with Better Auth. A SPA + Hono stack can omit the database. Hyperdrive pools production connections; every request creates its own client and releases it after the response stream completes or fails. Void's database migrations and auth are not used. SQLite, Prisma, MongoDB, D1, and Void Platform are excluded.

Before the first database-backed deployment, create a Hyperdrive configuration in the Cloudflare dashboard for the production database and turn **Query caching off**. Set its ID as `HYPERDRIVE_ID` in every deployment shell; `void.config.ts` binds the existing resource. Browser login can deploy this binding without a Hyperdrive-edit API token, but cannot create it. Automatic provisioning enables query caching, which does not invalidate reads after writes and can return stale todos or revoked sessions. Cache-disabled Hyperdrive still pools connections; keep caching disabled and use the same database as the migration URL.

After cloning, recreate local `.env` files from the generated README. A stack with a server runs `void prepare` in the deployed app to generate ignored Worker types; installation also runs it through `prepare`. Worker and Node tooling have separate TypeScript configs.

Follow the generated README to log in with `void connect --platform cloudflare` and set production server values with `void secret put`. Local `.env` values are never uploaded. For database-backed stacks, `HYPERDRIVE_ID='<cache-disabled-config-id>' DATABASE_URL='production-url' vp run deploy` checks both shell values before applying Drizzle migrations, builds the SPA when needed, then calls `void deploy`. The database URL must be explicitly present in the deployment shell, so a local `.env` cannot silently select the migration target. Keep both deployment values out of Worker secrets. Commit `void.lock.json`, which records your deployment state. Never regenerate it through vibestart maintenance. Generated projects contain no GitHub Actions.

In PowerShell, set `$env:HYPERDRIVE_ID = '<cache-disabled-config-id>'` and `$env:DATABASE_URL = 'production-url'`, then run `vp run deploy`. Stacks without a database need only `vp run deploy`, with no database URL or Hyperdrive.

`vibestart add void --dry-run` previews adding this deployment to a SPA without a server, which then runs on Workers. A project with a server keeps its Node.js or Bun runtime: `add` refuses to replace it, because moving server code to Workers is a migration. Docker cannot be replaced implicitly either.

## Electron [#electron]

<Tech href="https://www.electronjs.org" icon="electron" />

Electron wraps the SPA in a desktop window while sharing page code with the web app. `apps/desktop` contains the main process, preload, and packaging configuration. `packages/electron` defines IPC channels, payload schemas, and types.

Generated settings enable `contextIsolation` and `sandbox` and disable page-level `nodeIntegration`. IPC checks message sources; external links open in the system browser. Packaged apps load pages through `https://app.localhost` and proxy API requests when needed.

Electron uses the SPA frontend and electron-builder to produce distribution packages.
