## 按应用类型选择 [#by-use]

如果不确定从哪里开始，可以找到与你要构建的应用最接近的一行：

| 要构建的应用           | 可以考虑                                     | 原因                                       |
| ---------------------- | -------------------------------------------- | ------------------------------------------ |
| 内部工具或管理后台     | TanStack Router 单页应用、Hono、oRPC、SQLite | 部署简单，API 带类型，无需独立的数据库服务 |
| 页面需要被搜索引擎收录 | Next.js 或 TanStack Start                    | 页面在服务端渲染，内容随 HTML 一同返回     |
| 供其他客户端调用的 API | 无前端、Hono、OpenAPI                        | 标准 REST 接口，并自动生成接口文档         |
| 桌面应用               | TanStack Router 单页应用、Electron           | Electron 将单页应用打包为桌面窗口          |
| 多人同时写入的应用     | 使用 PostgreSQL 而非 SQLite                  | 独立的数据库服务，专为并发访问设计         |

其他情况下，直接采用 CLI 给出的推荐技术栈即可。

<Callout type="warn" title="先选定，再开发">
  框架、后端、API、数据库和认证方式决定了整个项目的结构，在创建时确定。之后通过
  `add` 只能添加 Knip、Ultracite 和 Docker。
</Callout>

## 兼容性 [#combinations]

部分选择依赖于其他选择：

- Electron 需要 TanStack Router 单页应用。
- 框架服务端需要 Next.js 或 TanStack Start。
- OpenAPI 需要 Hono。
- Bun 运行时仅适用于 Hono。

工作台和 CLI 会在你选择时应用这些规则。某项选择与之前的选择冲突时，会说明原因，并建议改动最少的解决方案。

## 集成原则 [#principles]

集成只选用已经成为当前标准、或正在成为新标准的开源工具，并要求它持续维护、类型完整、职责清晰。每项集成都必须支持本地开发，并能与所有可搭配的技术一起通过验证。

当更好的工具成为标准时，模板会在后续版本中切换过去，并移除被取代的工具，不保留兼容入口。例如，代码检查和格式化使用 Oxlint 与 Oxfmt，而不再提供 ESLint 与 Prettier。完整的选型标准见[为什么选择 vibestart](/docs/why#modern)。

具体的依赖版本，以生成项目中的 catalog 和锁文件为准。
