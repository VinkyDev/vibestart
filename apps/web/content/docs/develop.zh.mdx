大多数功能都会涉及应用的多个层次。本页以「为待办添加截止日期」为例，从数据库一直走到测试，再说明如何把同类工作交给编码 Agent 完成。

## 一次改动，贯穿各层 [#layers]

从数据层向外推进，每一步都能直接使用上一步得到的类型：表结构有了新字段，API 就能使用它的类型；API 接收了新字段，页面中的每次调用都会据此接受检查。在页面中试用之前，先执行 `vp run db:migrate`，把迁移应用到本地数据库。

## 与编码 Agent 协作 [#agent]

生成的 `AGENTS.md` 告诉编码 Agent 每类改动应该放在哪里、需要编写哪些测试，以及怎样才算完成。很多 Agent 会在会话开始时自动读取这个文件；如果你使用的 Agent 不会，请先让它阅读。

描述你想要的结果，而不是具体步骤，并说明如何确认完成：

```text title="提示词"
为待办添加可选的截止日期。用户在创建待办时设置，已过期的待办排在列表最前面。
遵循 AGENTS.md，补充其中要求的测试，在 vp run ready 通过后再结束。
```

Agent 报告完成后，重点检查以下几项：

- **迁移**：在应用到任何存有真实数据的数据库之前，先阅读生成的 SQL。
- **数据访问**：每个读写用户数据的 API 操作，都应受到保护并限定在当前用户范围内。
- **测试**：新行为应当伴随新测试。如果有测试被删除或放宽，应先问清原因，而不是直接接受。
- **最终检查**：自己运行 `vp run ready`，或在 Agent 的输出中确认它已经通过。

## 开发中的常用命令 [#commands]

| 任务                   | 命令                 |
| ---------------------- | -------------------- |
| 启动应用               | `vp run dev`         |
| 修改表结构后生成迁移   | `vp run db:generate` |
| 将迁移应用到本地数据库 | `vp run db:migrate`  |
| 格式、lint 与类型检查  | `vp check`           |
| 应用可自动修复的问题   | `vp check --fix`     |
| 运行单元测试与集成测试 | `vp test`            |
| 运行单个测试文件       | `vp test <文件>`     |
| 运行浏览器测试         | `vp run test:e2e`    |
| 提交前完整检查         | `vp run ready`       |

迭代过程中，只运行覆盖当前改动的最小范围检查；提交之前，再运行 `vp run ready`。

## 完成标准 [#done]

当改动涉及的每条路径都能完整运行、`AGENTS.md` 中的约定依然成立，并且 `vp run ready` 通过时，这次改动才算完成。该命令执行的检查、测试和生产构建，与每个组合在发布前通过的完全相同，因此你的改动会按项目创建时的标准接受检验。

测试的组织方式和各层覆盖的范围，见[测试与验证](/docs/testing)。
