生成项目中的测试描述用户和 API 调用方能够观察到的行为。期望结果来自需求和接口约定，而不是当前的实现，因此当行为被破坏时测试会失败，而单纯调整代码结构时测试依然通过。

## 三层测试 [#layers]

每一层测试驱动的应用范围各不相同。选择一层，查看它覆盖的内容：

    integration:

    unit: "单元测试检查自带分支的逻辑，不涉及网络或数据库。",

| 层级       | 覆盖范围                     | 示例                                 |
| ---------- | ---------------------------- | ------------------------------------ |
| 端到端测试 | 浏览器中的完整流程           | 注册后创建待办，刷新页面后仍能看到它 |
| 集成测试   | 接口的输入、输出、权限与错误 | 拒绝未登录请求，各用户的数据互不可见 |
| 单元测试   | 独立的分支逻辑               | 价格计算、权限规则、解析器和状态转换 |

项目包含哪些层级取决于技术栈。纯静态站点只有浏览器测试；带数据库的 API 会为每个接口操作增加集成测试；选择认证后，还会增加会话以及用户间数据隔离的测试。所有项目的单元测试和集成测试都由 Vitest 运行；Web 应用的端到端测试使用 Playwright 或 TesterArmy e2e，两者的对比见[测试工具](/docs/stack/testing#e2e-tests)。

## 为什么不追求单元测试数量 [#tradeoffs]

由 AI 批量补写的单元测试，常常逐个函数 mock 依赖、断言调用次数。这类测试让代码量成倍增加，却很少拦下真正的缺陷，反而会在每次重构时失败。因此，生成的项目把测试集中在两处：端到端测试保证产品能用，集成测试保证每个接口的输入、权限和错误处理正确；单元测试只用于确实含有分支逻辑的代码。

测试的数量不是目标。判断一条测试是否值得保留，只看一点：它描述的行为被破坏时，它会不会失败。两种做法的实际差别，见[为什么选择 vibestart](/docs/why#testing)中的对比演示。

## 测试原则 [#principles]

- **使用真实环境。** 集成测试经由真实的输入校验与权限检查调用 API，并连接真实数据库；端到端测试用真实浏览器访问运行中的服务。只有项目自身不运行的外部服务才可以使用替身，并且需要用测试固定它所模拟的请求与响应。
- **从两侧验证访问权限。** 每个受保护的操作，都要分别以未登录的调用方和另一位已登录用户进行测试。
- **先复现，再修复。** 修复缺陷时，先编写一个因该缺陷而失败的测试，再修改代码直到它通过。
- **测试行为，而非实现。** 测试应当在它所描述的行为被破坏时失败，并且在保持行为不变的重构之后依然通过。

## 运行测试 [#running]

开发过程中，只运行覆盖当前改动的最小范围，例如单个文件或 `vp test --changed`。提交之前，运行 `vp run ready` 完成全部检查、测试和生产构建。具体命令、隔离的测试环境以及排查失败的方法，见[测试工具](/docs/stack/testing)。

## 验证记录 [#verification]

每次发布前，所有支持的组合都会使用默认扩展生成、安装，并运行 `vp run ready`。运行通过后，生成一条验证记录，包含：

- 所有生成文件的指纹；
- 运行时的操作系统、架构和 Node.js 版本；
- 运行时间和耗时。

工作台会显示当前组合的验证记录，CLI 会在 `create` 结束时报告它（使用 `--json` 时位于 `verification` 字段）。指纹将记录与一份确切的输出绑定：如果文件不同，例如当前版本中尚无记录的组合，或选择了默认之外的扩展，则没有适用的记录。

<Callout title="记录的适用范围">
  验证记录只能说明项目在生成时通过了检查，不涵盖之后对代码、依赖或部署配置的修改。做出这些修改后，应以你自己运行的
  `vp run ready` 结果为准。
</Callout>
