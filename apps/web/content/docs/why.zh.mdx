## 现实问题 [#problems]

借助编码 Agent 开发应用，难点往往不在第一天，而在第三十天：功能越来越多，结构逐渐失序，Agent 每修复一个 bug，又会引入新的问题。

起点是原因之一。一个全栈 TypeScript 应用需要路由、API 层、带迁移的 ORM、会话管理、输入校验、lint 规则、覆盖接口与浏览器的测试，以及部署方式。每种搭配都有各自的配置细节；今天能够跑通的模板，也会随着依赖升级而逐渐失效。在配置松散的项目中，既没有规则告诉 Agent 改动应该放在哪里，也没有手段确认结果能够正常工作。

vibestart 为 Agent 和你提供一个更好的起点：经过精心挑选的前沿技术栈及其最佳实践，以及一套让 Agent 能够写出好代码的工程基础。

## 好代码养出好代码 [#theory]

vibestart 的核心理念很简单：**Agent 在优秀的代码基础上，才能写出高质量的代码。** 这由编码 Agent 的工作方式决定：

| Agent 会……             | 在配置松散的项目中         | 在 vibestart 项目中                              |
| ---------------------- | -------------------------- | ------------------------------------------------ |
| **模仿**周围已有的代码 | 照搬项目里随手留下的写法   | 每个文件都是风格一致、可以参照的范例             |
| **遵守**成文的规则     | 没有规则可循，只能即兴发挥 | 阅读 `AGENTS.md`，了解每类改动放在哪里、如何实现 |
| **依靠报错**修正自己   | 直到用户遇到问题才发现错误 | 类型、lint 和测试在几秒内指出问题所在            |

第三点最为关键。Agent 不会疲倦，但会犯错，而且往往错得很自信。决定最终代码质量的，是错误能否在第一时间被发现，并以 Agent 能够理解的方式反馈给它。

## 只选用前沿技术，并持续更新 [#modern]

vibestart 只提供已经成为当前标准、或正在成为新标准的技术。生成的项目使用带原生编译器的 TypeScript 7、启用 React Compiler 的 React 19、Drizzle ORM 1.0，用 Oxlint 和 Oxfmt 取代 ESLint 与 Prettier，并以 Vite+ 统一开发、检查、测试和构建。

当更好的工具成为标准时，模板会在后续版本中切换过去，并移除被取代的旧工具，而不是为了兼容将两者并存。每一项可选技术都需要满足以下标准：

- **前沿，而非过时。** 持续维护、被广泛采用，并代表生态的发展方向。
- **开源，不绑定厂商。** 项目可以在你自己的电脑和任意服务器上完整运行。托管服务可以通过配置接入，但不作为起步的前提。
- **能够验证。** 与所有可搭配的技术组合后，都能完成安装、检查、测试和构建。无法通过验证的技术不会提供。
- **适合 Agent 使用。** 类型完整、约定清晰、报错明确。在两个同样优秀的工具之间，优先选择能更早暴露错误的那一个。
- **每种能力只用一个库。** 不会出现两个状态管理库或两套 API 风格并存的情况。概念越少，人和 Agent 走错路的可能性就越小。

## 按需组合，而非复制模板 [#compose]

常见的脚手架以固定模板的形式提供：选一个最接近的，再删掉用不到的部分。vibestart 则将每项技术描述为一个集成，包括它的文件、依赖和约束，再根据你的选择组合出项目。单页应用可以搭配独立的 Hono 服务，TanStack Start 和 Next.js 可以由框架自身提供 API，项目也可以只包含 API。

工作台和 CLI 读取同一份集成注册表。选择相互冲突时（例如 Electron 搭配 Next.js），两者都会说明冲突原因，并给出改动最少的解决方案。

## 每个组合都经过验证 [#verification]

只有每种组合结果都能正常工作，按需组合才有意义。每次发布前，所有支持的组合都会被生成、安装，并依次通过类型检查、lint、测试、浏览器测试和生产构建。通过后，记录生成文件的指纹、运行环境和验证时间。

创建项目时，CLI 会将输出与该指纹比对，并报告适用的验证记录。记录只对刚生成的项目有效；修改代码、依赖或部署配置之后，应当由你运行 `vp run ready` 重新确认。详见[测试与验证](/docs/testing#verification)。

## 为什么只用 TypeScript [#typescript]

vibestart 只生成 TypeScript 项目，这是经过权衡的选择：

- **一种语言贯穿全栈。** 页面、服务端、表结构、输入校验、测试和配置全部使用 TypeScript，Agent 无需在多种语言之间切换，一个类型可以从数据表一直传递到展示它的页面。
- **类型是最快的反馈。** 在动态语言中，拼错一个字段要到运行时才会报错，甚至要等用户打开那个页面；在 TypeScript 中，写下代码的同时就会得到提示。
- **端到端的类型安全。** Drizzle 用 TypeScript 定义数据表，oRPC 从中推导接口类型，页面再从接口推导自己的类型，整个过程无需代码生成。修改一个字段名，所有用到它的地方都会报错。
- **Agent 最擅长的语言之一。** TypeScript 和 JavaScript 是使用最广泛的编程语言之一，Agent 见过的优质代码也最多。

静态类型发现你自己代码中的错误，Zod 的运行时校验拦截来自外部的错误数据，生成的项目同时依赖这两者。

## 只写有价值的测试 [#testing]

社区中流行着一种观点：AI 时代，单元测试已死，AI 写出的单元测试只会让代码量翻倍，却拦不住真正的问题。对于一类常见的单元测试，这样的批评并不为过。让 AI「补测试」时，它往往为每个函数写一个测试，mock 掉所有依赖，再断言某个函数被调用了一次。覆盖率看起来很高，产品出了问题测试照样全部通过，而每次重构都会让测试失败。

vibestart 并不放弃测试，而是把测试放在问题真正出现的地方：

- **端到端测试**覆盖范围最广。它在真实浏览器中注册、登录并完成操作，决定产品是否真正可用。
- **集成测试**覆盖每一个 API 操作，经由真实的 API 代码和数据库验证输入校验、错误码和权限。
- **单元测试**只留给真正含有分支逻辑的代码，例如价格计算、权限规则、状态机和解析器。

## 约定写在仓库里 [#conventions]

每个项目都包含按技术栈生成的 `AGENTS.md`，写明各目录的职责、一个请求如何流经整个应用、新的接口、数据表和页面分别放在哪里、一次改动需要哪些测试，以及怎样才算完成。开发者把它当作文档阅读，编码 Agent 把它当作指令执行。Codex 和 Cursor 会自动读取 `AGENTS.md`；使用 Claude Code 时，在 `CLAUDE.md` 中引用它即可。

`vp check` 统一执行格式、lint 和类型检查。Ultracite 为所用框架提供 lint 预设，Knip 报告未使用的文件、导出和依赖，避免项目不断堆积无用代码。两者默认启用，也可以不选。

## 创建之后仍可维护 [#maintenance]

大多数生成器在第一次提交后就不再参与。vibestart 会记录每个项目所基于的模板，以便合并后续的模板版本。`upgrade` 对比原始模板、你的项目和新模板，在写入任何文件之前先预览结果。遇到冲突时，升级会在修改文件前停止；未完成的操作可以继续，也可以回滚。详见 [CLI 参考](/docs/cli)。

## 与常见脚手架的区别 [#compare]

|                 | 常见的项目模板           | vibestart                              |
| --------------- | ------------------------ | -------------------------------------- |
| 技术栈          | 一套固定模板或少量选项   | 按需组合，冲突时说明原因并给出修正方案 |
| 能否运行        | 理论上可以               | 每个组合都通过了检查、测试和构建       |
| 给 Agent 的规则 | 没有，或是一段通用提示词 | 针对当前技术栈生成的 `AGENTS.md`       |
| 测试            | 没有，或只有示例文件     | 基于真实数据库的端到端测试与集成测试   |
| 创建之后        | 自行维护                 | 模板更新可合并进项目，写入前先预览     |

## vibestart 不做什么 [#scope]

- **不托管应用。** 生成的是普通的代码仓库，可以部署到任何地方。
- **不迁移生产数据。** 模板升级不会触碰数据库，迁移需要你审阅后自行执行。
- **不隐藏代码。** 生成的所有内容都可以阅读和修改，运行时不依赖 vibestart。
